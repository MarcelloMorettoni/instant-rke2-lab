Cilium splits into a small cluster-wide part and a per-node part that does the real work. Once per cluster: the Cilium Operator (a Deployment) handles cluster-wide chores: handing out pod IP ranges, maintaining Cilium's CRDs, and cleaning up identities nobody uses any more. Hubble Relay and the Hubble UI gather network flows from every node into one view. kgateway is drawn dashed because it is not part of Cilium. It is our Gateway API implementation and the front door of the demo cluster, with its own Envoy proxies. To Cilium, a kgateway proxy is just another pod with an identity, and we write policy for it like any other. On every node: the Cilium Agent (a DaemonSet) is the heart. It watches the Kubernetes API for pods, Services and policies, gives each pod a numeric security identity derived from its labels, and compiles all of it into eBPF programs and maps that it loads into the kernel. The CNI plugin is what kubelet calls when a pod starts, to plug it into that datapath. Cilium's own Envoy only gets traffic when an L7 rule needs it (HTTP paths, gRPC methods, Kafka topics). It is not the gateway. The Hubble server lives inside the agent and records every flow with its verdict. At the bottom, the eBPF datapath does routing, Service load-balancing (so kube-proxy and its iptables rules are gone), network policy and optional transparent encryption, all inside the kernel.

The cluster denies everything by default. Every pod has a security identity derived from its labels and namespace, the kgateway proxy included, and policy is written against those identities, not IP addresses. Default deny: right after step 01, the apps can't talk to anyone, not even DNS. If the cluster also polices traffic from the node, they don't even turn Ready. Step 02: each tenant gets probes from its node, its own pods and DNS. The other tenant is never mentioned, so it stays unreachable in both directions. Step 03, the front door: the proxy may fetch its configuration from the kgateway controller (xDS on 9977) and call both apps on 8080, and each app accepts the proxy. The tenants' outgoing rules don't include the proxy, so neither tenant can take a detour through the gateway to reach the other. Step 04 is a deliberate mistake: someone allows tenant a to call tenant b on both ends, and it works. Isolation by default deny alone lasts only until someone adds an allow. Step 05, the guardrail: explicit deny rules between the two tenants. In Cilium a deny always beats an allow, so the mistake, still in place, no longer opens anything. matrix.sh shows the result after every step, and Hubble and cilium-dbg show each drop with its reason and identities.
