# ADR 0010 · Kafka in the cluster, between the collector tiers

**Status:** accepted · **Date:** 2026-10-05 · **Supersedes:** [0006](0006-no-kafka-buffer.md)

## Context
ADR 0006 left Kafka out: every hop already had a disk buffer. The platform team now wants
a bus in the write path, and wants it **local**: running in the cluster, the same way in
the generic and the Azure installations ([10](../10-installations.md)). Two gaps of the no-bus
design matter most:
- while the gateways or Loki are down, the backlog sits in each **node's** agent queue.
  Losing a node during an outage loses that node's backlog;
- the stream can't be **replayed** or read by a second consumer (SIEM, data lake).

## Decision
**Kafka, run by Strimzi in namespace `kafka`, between the OTel agents and the OTel gateways.**
- The operators chart installs the Strimzi operator (1.2.0), watching only `kafka`. The
  platform chart creates cluster `logs`:
  - Kafka 4.3.1 in KRaft mode: 3 controllers and 3 brokers, one per zone (`rack`), on
    zonal SSDs;
  - replication factor 3, `min.insync.replicas` 2, no unclean leader election.
- **One topic, `otel-logs`**: 24 partitions, 24 h retention, OTLP protobuf. The agents key
  each message by its resource attributes (pod + container), so a stream stays in order on
  one partition.
- **Agents produce** with `acks=all`, zstd, through their persistent node queue, which now
  only covers a Kafka outage.
- **Gateways consume** as one consumer group, one worker per partition. They commit an
  offset only once the record is in its tenant's persistent queue. The per-tenant queues
  and exporters to Loki are unchanged, so tenant isolation toward Loki is unchanged.
- **Security**:
  - one TLS listener (:9093) with SCRAM-SHA-512;
  - two users with ACLs: `otel-agent` may only write the topic, `otel-gateway` may only
    read it;
  - Strimzi's NetworkPolicy admits only the agent and gateway pods;
  - the listener certificate and the passwords are generated by the chart (`kafka-client`
    Secrets next to each collector).

  The tenant is still decided by the agent from the namespace (ADR 0002). Nobody else can
  write to the topic.
- `kafka.enabled: true` is the default. `environments/overlays/no-kafka.yaml` restores the
  ADR 0006 pipeline (agents → gateways over OTLP) without other changes.

## Why in the cluster, not Event Hubs
- The **same** installation works with and without Azure. The generic profile has no Azure
  dependency, and the team validates one backend, not two.
- The OpenTelemetry Kafka exporter/receiver authenticate with SCRAM or mTLS out of the box.
  Event Hubs' Kafka endpoint needs Entra OAuth (or connection strings, which the bank avoids).
- Data stays in the cluster's network, disks and encryption, like the rest of the pipeline.

## Consequences
- **Plus:** the backlog of an outage is replicated across 3 zones instead of sitting on
  nodes. Up to 24 h of Loki or gateway outage is replayed in order. A second consumer can
  read the topic with its own group and ACL.
- **Minus:** a third stateful system to run:
  - brokers, KRaft quorum, disks;
  - Strimzi and Kafka upgrades;
  - capacity planning ([05](../05-sizing-and-capacity.md#kafka));
  - its own alerts (`KafkaBrokersMissing`, `KafkaUnderReplicatedPartitions`,
    `KafkaConsumerLagHigh`).

  Kafka also keeps a second copy of every log line, for 24 h.
- **Isolation limit:** partitions are shared between tenants. If one tenant's gateway queue
  is full, the gateway stops committing on the partitions carrying that tenant and retries
  them (`error_backoff`). The other tenants on those partitions wait with it; they are not
  lost. `OtelGatewayTenantQueueFilling` fires at 50 %, long before that.
- **Credentials and the listener certificate** are generated once and kept across upgrades
  (Helm lookup). Rotate them by deleting the Secrets and upgrading
  ([06](../06-operations-runbook.md#kafka)).

## Not chosen
- **Loki's own Kafka ingest** (`-distributor.kafka-writes-enabled`, block builders): still
  experimental in Loki 3.6. Revisit when it is GA.
- **One topic per tenant**: better isolation, but hundreds of topics and a gateway receiver
  per topic. Revisit if the shared-partition limit above is hit in practice.
